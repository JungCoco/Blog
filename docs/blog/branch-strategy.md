# 1인 개발 블로그 프로젝트에서 브랜치 전략을 바꾼 이유

## 배경

개인 블로그를 모노레포(pnpm workspace + Turborepo)로 구성하고 있다. `apps/blog`, `apps/admin`, `packages/design-system` 세 프로젝트가 하나의 저장소에 들어있는 구조다.

처음에는 "프로젝트별로 브랜치를 나누는 게 깔끔하지 않을까?"라고 생각했다. 그래서 이런 브랜치 구조를 잡았다.

```
main
├── feature/v0/blog       ← 블로그 프론트엔드 작업
├── feature/v0/admin      ← 어드민/에디터 작업
├── feature/design-system ← 디자인 시스템 작업
├── feature/db            ← DB 스키마 설계
├── feature/ui-prototype  ← UI 프로토타입
└── ...기타 실험 브랜치들
```

한 달 정도 이 방식으로 개발했다. 결론부터 말하면, 바꾸기로 했다.

## 문제: 브랜치가 많다고 정리되는 게 아니다

### 1. 경계가 무너진다

모노레포에서 앱별로 브랜치를 나누면 이론상 깔끔해 보인다. 하지만 실제로는 한 작업이 여러 프로젝트에 걸치는 경우가 대부분이다.

에디터에서 글을 저장하는 기능을 만들면 `apps/admin`의 에디터 코드도 고치고, `apps/blog`에서 그 데이터를 렌더링하는 부분도 같이 수정해야 한다. 디자인 시스템에 레이아웃 컴포넌트를 추가하면 `packages/design-system`과 `apps/blog`를 동시에 건드려야 한다.

결국 `feature/v0/admin` 브랜치에서 작업하다가 blog 쪽 코드도 고치게 되고, 커밋 히스토리를 보면 브랜치 이름과 실제 변경 범위가 일치하지 않는다.

### 2. 머지 타이밍이 꼬인다

블로그 브랜치에서 만든 변경이 어드민 브랜치에서도 필요할 때, 선택지는 두 가지다. main에 먼저 머지하고 다른 브랜치에서 pull하거나, 브랜치 간 직접 머지하거나.

1인 개발에서 이걸 매번 신경 쓰는 건 오버헤드다. 실제로 나는 main 업데이트 없이 feature 브랜치에서 계속 작업하게 됐고, main은 중간 시점에 멈춰버렸다.

### 3. 죽은 브랜치가 쌓인다

실험하다 중단한 `feature/design-system-v2`, 역할이 끝난 `feature/ui-prototype`, 테스트용 `admin/test/editor` 같은 브랜치가 정리되지 않고 남아있다. 원격에는 `env/initial-setting`, `refactor/monorepo-migration` 같은 잔재도 있다.

브랜치 목록을 보면 13개인데, 실제로 의미 있는 건 2~3개뿐이다.

## 새로운 전략: 단순하게

### V0 단계 (현재 ~ 출시)

지금은 `feature/v0/blog` 하나에서 blog + admin 작업을 같이 한다. 이미 디렉토리로 분리돼 있으니까 브랜치로 또 나눌 이유가 없다.

```
main ──────────────────── ← V0 완성 시 머지 + 태그(v0.1.0)
  └── feature/v0/blog    ← 모든 V0 작업
```

영역 구분은 커밋 메시지의 scope로 한다.

```
feat(blog): 메인 페이지 반응형 적용
feat(admin): 글 수정 기능 추가
feat(ds): Typography 컴포넌트 추출
```

### V1 단계 (출시 이후)

Trunk-based 전략으로 전환한다.

```
main (항상 배포 가능)
  ├── feature/xxx → 1~3일 내 머지 → 삭제
  ├── fix/xxx     → 핫픽스 → 삭제
  └── tags: v0.1.0, v1.0.0, ...
```

핵심 규칙은 세 가지다.

1. main은 항상 배포 가능한 상태를 유지한다.
2. feature 브랜치는 1~3일 이내에 머지하고 삭제한다. 오래 살려두지 않는다.
3. 릴리스 시점마다 시맨틱 버전 태그를 찍는다.

## 왜 이렇게 바꾸는가

**모노레포는 이미 디렉토리로 분리돼 있다.** `apps/blog`과 `apps/admin`이 폴더로 나뉘어 있는데 브랜치까지 나누면 이중 분리다. 디렉토리 구조가 곧 관심사의 분리이고, 브랜치는 "작업 단위"로 쓰는 게 맞다.

**1인 개발에서 브랜치 관리 비용은 순수 오버헤드다.** 코드 리뷰도 없고 CI/CD 파이프라인도 없는 상태에서, 브랜치를 정교하게 나누는 건 형식만 갖추는 일이다. 그 시간에 코드를 한 줄이라도 더 쓰는 게 낫다.

**Toss의 TDS도 서비스 운영 속에서 나왔다.** 처음부터 완벽한 구조를 만들고 시작한 게 아니라, 실제 제품을 만들면서 반복 패턴을 추출한 거다. 브랜치 전략도 마찬가지로, 지금 규모에 맞는 가장 단순한 방식을 쓰고, 규모가 커지면 그때 조정하면 된다.

## 정리 계획

V0 출시 후 아래 브랜치들을 정리할 예정이다.

| 브랜치 | 조치 | 이유 |
|---|---|---|
| `feature/design-system` | 삭제 | main과 동일 지점 |
| `feature/design-system-v2` | 삭제 | 중단된 실험 |
| `feature/ui-prototype` | 삭제 | main에 반영 완료 |
| `feature/db` | main 머지 후 삭제 | 스키마 문서 보존 |
| `admin/test/editor` | 삭제 | 테스트 종료 |
| `env/initial-setting` | 삭제 | 초기 세팅 잔재 |
| `refactor/monorepo-migration` | 삭제 | 완료된 작업 |

## 마무리

완벽한 구조를 먼저 갖추고 싶은 욕심이 있었다. 하지만 V0의 목표는 "글을 쓸 수 있는 상태"를 만드는 것이다. 브랜치 전략은 그 목표를 방해하지 않는 선에서 가장 단순한 게 최선이다.

일단 만들고, 쓰고, 부딪히고, 그때 바꾸자.
